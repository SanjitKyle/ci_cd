🚀 Week 1: GitHub Actions & CI/CD Fundamentals

Your complete revision notes, definitions, and code examples for Week 1.

1. What is CI/CD?

Continuous Integration (CI): The automated process of checking code out, installing dependencies, and running tests every time a developer pushes code.

Continuous Deployment (CD): The automated process of taking that tested code and deploying it safely to a live server.

Real World Goal: Stop developers from manually pushing broken code to production. Let a robot (GitHub Actions) test it first!

2. The 5 Core Building Blocks

Block YAML Keyword Definition & Real World Meaning
Workflow name: The name of the entire automated pipeline file.
Trigger on: The "sensor" that wakes up the workflow (e.g., waiting for a push to the main branch).
Jobs jobs: The individual "workers". Each job runs on a totally separate computer.
Runner runs-on: Renting a fresh, blank computer from GitHub's servers (e.g., ubuntu-latest).
Steps steps: The chronological instruction manual we give to the blank computer.

3. Crucial Rules of YAML & CI/CD

1. The Spacing Rule: YAML does not use brackets {}. It uses SPACES. Every time something is "inside" something else, it must be indented by exactly 2 spaces. If you mess up the spaces, the workflow crashes.
2. Exit Codes (Quality Gates): GitHub decides if a step passed or failed by looking at terminal Exit Codes.
Exit Code 0 = Success. Pipeline continues.
Exit Code 1 = Failure. Pipeline stops immediately and turns Red ❌.
3. No Infinite Loops: You can never run commands like npm start or nodemon in CI/CD. The terminal must finish its job and close. If it stays open forever, the server hangs and wastes compute minutes.

4. The Most Important Commands

The Checkout Step

Because GitHub gives us a 100% blank computer, we MUST tell it to download our code first. We do this using a pre-built action:

- uses: actions/checkout@v4

Running Terminal Commands

Use the run: keyword to type anything you would normally type in your own terminal. Use the pipe | symbol to run multiple lines of code.

- run: | echo "This is line 1" npm install npm test

5. Advanced Week 1 Concepts

Multi-Job Pipelines (The "needs" keyword)

By default, GitHub runs all jobs at the exact same time to save time. The needs keyword acts like a traffic light, telling a job to WAIT for another job to finish successfully before it starts.

Secrets & Passwords

Never type passwords in YAML. Store them securely in GitHub Repo Settings → Secrets. Pull them into the code using ${{ secrets.SECRET_NAME }}. GitHub will mask them with *** in logs.

6. The Ultimate Week 1 Master Pipeline

Here is an example combining everything you learned:

name: Production Pipeline on: push: branches: - main # Only wake up on main branch pushes workflow_dispatch: # Adds manual run button jobs: # Job 1: Testing test_job: runs-on: ubuntu-latest steps: - name: Checkout Code uses: actions/checkout@v4 - name: Run tests run: npm test # Will throw Exit Code 1 if it fails # Job 2: Deployment deploy_job: needs: test_job # Wait for test_job to finish! runs-on: ubuntu-latest steps: - name: Deploy with Secret env: PASSWORD: ${{ secrets.MY_DB_PASS }} run: | echo "Deploying..." echo "Using password: $PASSWORD" # Shows as ***

7. YAML Copy-Paste Templates

Use these templates for quick revision or to copy-paste into your future projects!

Template 1: Branch Filtering (Only run on main)

Stops the pipeline from running when developers push to test branches.

on: push: branches: - main

Template 2: Path Filtering (Ignore README changes)

Save compute time by NOT running tests if someone only changes a markdown file.

on: push: paths-ignore: - '**.md'

Template 3: Multi-Line Terminal Commands

Use the pipe | symbol to run multiple terminal commands in one step.

steps: - name: Install and Test run: | npm install npm test echo "All done!"

Template 4: Using GitHub Secrets Safely

Always load secrets into the env block first so GitHub can hide them.

steps: - name: Login to Database env: DB_PASS: ${{ secrets.DATABASE_PASSWORD }} run: | echo "Logging in..." echo "Password is $DB_PASS"

Template 5: Setting up Node.js

A very common step to prepare a Linux machine for a JavaScript project.

steps: - name: Set up Node uses: actions/setup-node@v4 with: node-version: 20

Exercise 1: Your First Action

The simplest workflow. Triggered on push, rented a Linux machine, checked out code, and printed a message.

name: Exercise 1 - My First Action on: push jobs: first_job: runs-on: ubuntu-latest steps: - name: Step 1 - Get code uses: actions/checkout@v4 - name: Step 2 - Say Hello run: echo "Hello World from GitHub Actions!"

Exercise 2: Path Filtering & Manual Triggers

Added workflow_dispatch so we could click a button to run it, and ignored .md files.

name: Exercise 2 - Path filtering on: push: paths-ignore: - '**.md' workflow_dispatch: jobs: second_job: runs-on: ubuntu-latest steps: - run: echo "I only run when code changes, not markdown!"

Exercise 3: Quality Gates (Node.js Testing)

Set up a Node.js environment, installed packages, and ran tests. If tests failed (Exit Code 1), the pipeline crashed.

name: Exercise 3 - Quality Gate on: push jobs: run_quality_test: runs-on: ubuntu-latest steps: - name: Step 1 - Checkout repository uses: actions/checkout@v4 - name: Step 2 - Setup node js uses: actions/setup-node@v4 with: node-version: 20 - name: Step 3 - Install dependency run: npm ci - name: Step 4 - Execute the unit test run: npm test

Exercise 4: Environment Variables & Secrets

Learning how to store public variables (APP_NAME) and hide private passwords using GitHub Secrets.

name: Exercise 4 Environment Variables and Secrets on: push: branches: - main workflow_dispatch: jobs: secrets_jobs: runs-on: ubuntu-latest env: APP_NAME: "Github actions Learning APP" APP_ENV: "staging" steps: - name: Step 1 - Checkout uses: actions/checkout@v4 - name: Step 2 - use encrypt secret safely env: MY_SECRET: ${{secrets.MY_API_KEY}} run: | echo "Connecting to external database" echo "Secret Token value is: $MY_SECRET"

Exercise 5: Multi-Job Pipelines (The Finale!)

Using the needs: keyword to create a visual graph and stop the deploy job if the test job fails.

name: Exercise 5 - Multi-Job Pipelines on: push: branches: - main jobs: test_job: runs-on: ubuntu-latest steps: - name: Run tests run: echo "Tests passed! ✅" deploy_job: runs-on: ubuntu-latest needs: test_job steps: - name: Deploy to production run: echo "Deploying application to the server... 🚀"
