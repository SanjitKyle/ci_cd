CI/CD Master Handbook

In-Depth Guide to GitHub Actions: Weeks 1 & 2

📘 WEEK 1: The Core Fundamentals

1. The Anatomy of GitHub Actions

A pipeline is built using strict YAML syntax (indentation using exactly 2 spaces). Understanding the hierarchy is the most important skill for a DevOps engineer.

ComponentDefinitionDeep Dive Knowledge
Trigger (on:) When the workflow runs. You can filter triggers aggressively. paths-ignore: '**.md' prevents the pipeline from wasting compute time if a developer only updates the README.
Runner (runs-on:) The virtual machine. These are ephemeral (temporary) environments. When the job finishes, GitHub physically destroys the virtual machine. Nothing is saved permanently.
Actions (uses:) Pre-packaged code. actions/checkout@v4 is mandatory. Because the runner is a blank slate, this action securely clones your Git repository into the runner's memory so it can be tested.

2. Quality Gates & Exit Codes

The Underlying Mechanics: GitHub Actions does not actually know if your Node.js code is good or bad. It only listens to the Operating System's Exit Codes.

When you run npm test, if the tests pass, Node.js silently sends Exit Code 0 to Linux. GitHub sees the 0 and paints the step Green ✅. If a test fails, Node.js sends Exit Code 1. GitHub sees the 1, immediately kills the runner, and paints the step Red ❌.
Pro Tip: Never run background processes like nodemon or infinite server loops in CI/CD. The step will hang forever waiting for an Exit Code that never comes, wasting your company's money.

3. Managing Secrets & Environment Variables

In production, you never hardcode passwords. You inject them dynamically.

env: APP_NAME: "My Production App" # Public variable steps: - name: Login env: DB_PASS: ${{ secrets.DB_PASSWORD }} # Secure private variable run: echo "Logging in with $DB_PASS"
Real World Context: When you use ${{ secrets... }}, GitHub encrypts it. Even if you try to print it to the terminal using echo, GitHub intercepts the log and masks it as *** so hackers cannot read your build logs.

🚀 WEEK 2: Optimization & Production Power

4. The Matrix Strategy

The Matrix allows you to run a single job across multiple configurations simultaneously.

Why depth matters here: A junior developer writes 3 different jobs to test Node 16, 18, and 20. A Senior developer writes 1 job using a Matrix. This keeps the YAML file DRY (Don't Repeat Yourself) and ensures all tests run in parallel, cutting test time by 66%.
strategy: matrix: os: [ubuntu-latest, windows-latest] node: [18, 20] # This creates a 2x2 grid. GitHub will automatically spin up 4 computers to test every combination!

5. Ephemeral Storage & Artifacts

Because runners are destroyed after a job finishes (Ephemeral Environments), files do not persist between Jobs.

The Problem: Job 1 (Build) compiles your code into a ZIP. Job 2 (Deploy) needs that ZIP. But Job 2 is running on a totally different computer!
The Solution: actions/upload-artifact saves the ZIP to GitHub's permanent cloud storage. actions/download-artifact pulls it down into Job 2.

6. Pipeline Optimization (Caching)

Caching saves heavy folders (like node_modules) so they don't have to be downloaded from the internet on every single run.

How Cache Keys actually work:
key: node-cache-${{ hashFiles('package-lock.json') }}

The hashFiles function reads your package-lock file and generates a unique string of gibberish (a hash). If you install a new NPM package, the lock file changes, the hash changes, and GitHub knows it needs to create a brand new cache! If the file hasn't changed, it instantly loads the old cache.

7. Docker Containerization (The Holy Grail)

Docker is the industry standard for deploying backend code.

The "It works on my machine" Problem: You write code on a Windows laptop. It works perfectly. You deploy it to an AWS Linux server. It crashes because the server has the wrong Node.js version installed.

The Docker Solution: A Dockerfile packages your code, Node.js, and a mini Linux Operating System into a single, indestructible box (a Container). Because the operating system is inside the box, it is 100% guaranteed to run exactly the same way on AWS as it did on your laptop.
# Build the box (reads the Dockerfile) docker build -t my-app . # Turn the box on docker run my-app

📂 Real-World Production YAML Templates

These are exact templates you would find in a real company's codebase for backend applications.

Template 1: The "Pull Request Checker" (Backend CI)

Scenario: You have a team of developers. Before anyone is allowed to merge their branch into main, this pipeline automatically runs to ensure they didn't break the backend tests or formatting.

name: Backend CI Quality Gate on: pull_request: branches: [ "main", "staging" ] jobs: test_backend: runs-on: ubuntu-latest steps: - name: Checkout Code uses: actions/checkout@v4 - name: Setup Node.js uses: actions/setup-node@v4 with: node-version: '20' cache: 'npm' # Modern 1-line caching! - name: Install Dependencies run: npm ci - name: Check Code Formatting (Lint) run: npm run lint - name: Run Unit Tests run: npm test

Template 2: The "AWS Docker Deployer" (Backend CD)

Scenario: You just merged code into main. This pipeline tests the code, builds it into an indestructible Docker container, securely logs into AWS via OIDC, and uploads the container to AWS ECR.

name: Production AWS Deployment on: push: branches: [ "main" ] # Required for OIDC passwordless AWS login permissions: id-token: write contents: read jobs: build_and_deploy: runs-on: ubuntu-latest steps: - name: Checkout Code uses: actions/checkout@v4 - name: Run Backend Tests run: | npm ci npm test - name: Secure Login to AWS (OIDC) uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::123456789012:role/ProductionDeployRole aws-region: us-east-1 - name: Login to Amazon ECR (Docker Vault) id: login-ecr uses: aws-actions/amazon-ecr-login@v2 - name: Build, tag, and push Docker image to AWS env: ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }} ECR_REPOSITORY: my-backend-app IMAGE_TAG: ${{ github.sha }} # Tags container with the Git commit ID run: | docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG . docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG

Template 3: "The Dental Clinic Backend" (Node.js + Database)

Scenario: You are building a Node.js backend for a Dental Clinic Management system. It handles patient appointments and billing. Because it is a real backend, you cannot test it without a database! This template shows how to use Service Containers to spin up a temporary PostgreSQL database just for your tests.

name: Dental Clinic Backend CI/CD on: push: branches: [ "main" ] jobs: test_and_deploy: runs-on: ubuntu-latest # ADVANCED REAL-WORLD FEATURE: Service Containers # This spins up a blank database next to our code for testing! services: postgres: image: postgres:15 env: POSTGRES_DB: clinic_test_db POSTGRES_PASSWORD: supersecret ports: - 5432:5432 options: > --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5 steps: - name: Checkout Clinic Code uses: actions/checkout@v4 - name: Setup Node.js uses: actions/setup-node@v4 with: node-version: '20' cache: 'npm' - name: Install NPM Dependencies run: npm ci - name: Run Database Migrations (Create Patient Tables) env: DATABASE_URL: postgres://postgres:supersecret@localhost:5432/clinic_test_db run: npm run migrate - name: Run Backend Integration Tests env: DATABASE_URL: postgres://postgres:supersecret@localhost:5432/clinic_test_db JWT_SECRET: ${{ secrets.TEST_JWT_SECRET }} # For doctor login tests run: npm test - name: Build Docker Container for AWS run: | echo "Tests passed! Packaging the clinic app..." docker build -t dental-clinic-backend .
